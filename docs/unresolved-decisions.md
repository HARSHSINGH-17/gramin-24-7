|---|---|---|---|
| Initialize Git and create an initial baseline commit? | Yes, outside this architecture task. | Which files own the event schema and API contract? | JSON Schema files under `schemas/`; human-readable contracts under `docs/`; backend models and validators will later reference the schemas rather than duplicate them. | Separates machine validation from API and architecture explanation and gives contracts stable review locations. | Backend implementation approval |
| How does existing localStorage coexist with server-backed RPM data? | Keep current localStorage data for existing demo patient/medicine/report workflows. Store future RPM cache and outbound queue separately, preferably in IndexedDB, with server data marked as cached and queue state marked independently. | Avoids destructive migration and prevents a local write from being mistaken for server delivery. A migration requires consent, identity mapping, and privacy review. | Data migration design |
| Is Flutter mandatory under competition rules? | No evidence in this repository makes Flutter mandatory. Continue with React/Vite unless the official rules explicitly require Flutter; obtain written confirmation before starting a second frontend or migration. | Existing functionality is React-based and a migration would add risk without a confirmed requirement. | Competition-rule confirmation |
| Is Firebase the canonical database? | Not decided. Treat Firebase as a future adapter for authentication and/or persistence only after backend ownership, audit requirements, and deployment constraints are approved. | The FastAPI boundary must remain authoritative for validation and alert decisions. | Backend/persistence decision |
| Are thresholds clinically valid? | No. Use versioned demonstration rules only, label them non-clinical, and require clinician review before pilot use. | Software threshold behavior is not clinical validation or medical advice. | Clinical safety review |
| What clock-skew policy applies? | For the Phase 2C contract layer, accept and preserve future timestamps while recording server receipt time; before durable production persistence, decide whether future events are rejected or quarantined and retain late historical events with explicit quality metadata. | Offline devices and rural connectivity make late and out-of-order delivery expected, but no clinical cutoff should be invented in the validation layer. | Backend time policy |
| What patient-not-found response is used? | Decide globally whether unauthorized and unknown patients return the same `404` or an authorization-safe empty response. | Prevents patient enumeration while keeping API behavior predictable. | Security review |
| How should timestamp format enforcement be made portable in JSON Schema? | Keep backend/Pydantic timestamp validation strict now; consider a contract revision adding an explicit RFC 3339 pattern or standardize validator configuration because the installed Python `jsonschema` path does not enforce the declared `format: date-time` during these tests. | The Phase 2A contract requires timezone information, but format-only enforcement varies by validator. Do not change the version 1.0 schema silently. | Contract revision review |
| How should active demonstration alerts be reopened after resolution? | Implemented for Phase 5: only `open` and `acknowledged` alerts participate in active deduplication; a later abnormal event after explicit resolution creates a new alert. | This preserves explicit lifecycle actions and avoids treating a normal reading as resolution. | Clinical workflow review |
| What is the local persistence boundary? | SQLite is the approved local Phase 5 repository at `backend/data/pahaadcare.sqlite3`, configurable with `PAHAADCARE_DB_PATH`; it remains a prototype store and is not a production deployment plan. | This provides restart-safe behavior without introducing cloud infrastructure. | Future deployment design |
| What happens after an alert is resolved? | A later event with the same condition creates a new alert; normal readings do not resolve alerts automatically. | Explicit clinician action and new-condition identity must remain distinct from measurement processing. | Clinical workflow review |
| What identity system is used beyond the prototype? | Phase 6 uses one environment-configured scrypt-hashed demo account and signed short-lived JWTs for local testing only. Replace it with a reviewed identity provider, account lifecycle, MFA, and role governance before real data. | This avoids fake patient registration while protecting the current prototype routes. | Deployment/security review |
| How is the local audit trail used operationally? | SQLite audit records cover prototype alert mutations and are not a regulatory compliance claim. Export, retention, tamper resistance, and centralized monitoring remain future deployment requirements. | Local persistence supports testing and restart behavior but does not provide production audit assurance. | Privacy/security review |
| What is the batch synchronization execution policy? | Implemented in Milestone 1: Best-effort partial success. Valid events are persisted and ingested even if a sibling event in the batch encounters a conflict or authorization failure. | Intermittent connectivity in Himalayan villages means network windows are fleeting; valid patient vitals must not be starved because of a single conflicting payload. | Milestone 1 architecture |
| How is the patient registry managed in Milestone 1? | Implemented in Milestone 1: SQLite `patients` table seeded with `PC-SYNTH01` and `PC-DEMO01`, auto-populated when new events are ingested. | Provides a durable, persistent patient list for `GET /api/v1/patients` without inventing an artificial production identity provider prematurely. | Milestone 1 architecture |
| How is test fixture isolation guaranteed across full-suite test runs? | Implemented in Milestone 1: `browser_env` captures original `os.environ` and `main.settings` and restores them in teardown; route dependencies resolve settings dynamically via callable. | Eliminates cross-test pollution and enables the full 110-test suite to pass reliably in a single runner invocation. | Milestone 1 test strategy |
